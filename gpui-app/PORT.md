# GompassQL → GPUI 포팅 현황

브랜치: `gpui-port`. 웹앱(React + PixiJS/WebGL + GraphViz-WASM)을 Rust + GPUI로 재작성.
방침: **픽셀 동일 UI가 아니라 기능 동등성** (사용자 확인됨). 성능 기준: `schema.docs.graphql`(72k 라인, GitHub 스키마).

## 구조

```
gpui-app/
  core/            # gompass-core — GPUI 무관 순수 로직 (cargo test -p gompass-core)
    src/graph.rs   # sdl-to-graph.ts 포팅: SDL → ParsedGraph (+ until/reachable/components)
    src/layout.rs  # 계층형(Sugiyama) 레이아웃 — GraphViz WASM + 청킹 오케스트레이터 대체
    src/ranking.rs # network simplex 레이어링(최소 총 스팬) — 옵트인, 아래 참조
  src/
    model.rs       # 뷰모델: 카드 지오메트리 단일 소스 (페인트/히트테스트 공유)
    canvas.rs      # GPUI 캔버스: 팬/줌/호버/클릭 + 페인팅 (텍스트 LOD, 컬링)
    about.rs       # About 라우트 — 이 빌드의 렌더·레이아웃 기법과 사용 팁
    main.rs        # 엔트리: SDL 로드 → 파싱 → 레이아웃 → 윈도우
```

## 웹앱 대비 의도적으로 버린 것 (WebGL 브라우저 한계 우회 코드)

- 텍스처 캐시/DPR 버킷/모션 게이트/스프라이트 LOD 플레이스홀더 — GPUI는 즉시 페인팅이라 불필요
- SDF 글리프 아틀라스 — GPUI 텍스트 시스템이 대체
- 레이아웃 워커 풀 + 컴포넌트 청킹(500노드 단위 이등분) — 네이티브 레이아웃은 한 방에 처리
- IndexedDB 레이아웃 캐시 — 네이티브 속도면 필요성 재평가 (필요시 파일 캐시)

## 개선(최적화) 사항

- 엣지가 dot 스플라인 대신 **필드 행 포트에 앵커된** 베지어 (소스 필드 행 중심에서 출발)
- 카드 행 지오메트리 수식이 한 곳(model.rs `Card::row_y`/`row_at`) — 웹앱은 같은 수식이 3벌
- 레이아웃/파싱 모두 네이티브 — WASM OOM, 워커 직렬화 오버헤드 소멸

## 성능 목표: 모든 줌에서 120fps (프레임당 8.3ms)

`GOMPASS_PERF=1`이 프레임 비용(`perf: k=…`)과 레이아웃 품질(`layout: …`)을 같이 찍는다.
GitHub 스키마(804 노드 / 3960 엣지) 기준, k=0.02~3.0 전 구간 **4.9~7.8ms**.

프레임을 지배하던 것은 언제나 엣지였고, 세 가지로 잡았다.

1. **큐빅을 GPUI에 넘기지 않는다.** `PathBuilder::cubic_bezier_to`는 선분 대비 엣지당 약
   5배 비싸고 화면 크기에 비례해 더 비싸진다(k=0.6에서 17.7ms 중 17ms). 대신
   `canvas.rs::flatten_cubic`이 2차 차분으로 화면상 굽은 정도를 재서 필요한 만큼만
   선분을 낸다.
2. **프레임 예산.** 이상적 허용오차(0.35px)로 먼저 견적을 내고, 예산(`SEG_BUDGET`)을
   넘으면 초과분의 제곱만큼 허용오차를 완화한다(n ∝ 1/√tol). 엣지가 이미 예산 안이면
   허용오차는 이상값 그대로다 — 실제로 k≥0.45 구간은 0.6px대를 유지하고, 전체 스키마가
   한 화면에 들어오는 저줌에서만 3px대로 올라간다(엣지 폭 1px, 길이 700px 스케일).
3. **웨이포인트 완화.** 레인은 랭크마다 따로 잡히므로 경로가 지그재그로 나온다.
   `layout.rs::smooth_chain`이 내부 노드를 완화(20패스)하고 `simplify`가 남은 직선
   구간을 접는다. 렌더가 평탄화할 곡률이 줄어들 뿐 아니라 교차 수도 같이 줄었다.

## 레이아웃 복잡도

복잡도 = 엣지가 길수록, 무관한 카드를 가로지를수록 나쁨(사용자 정의). 측정 지표는
`avg len` / `crossings`(엣지가 지나가는 남의 카드 수, 호길이 32px 균등 샘플).

| 변경 | avg len | crossings/edge | world |
|---|---|---|---|
| 시작점 (longest-path 랭킹) | 8399 | — | 26981×21417 |
| BFS 깊이 랭킹 + median 조임 | 5110 | 5.59 | 14746×24649 |
| 가상 노드 높이 0 (레인은 상자가 아니다) | 5147 | 6.03 | 14746×22106 |
| 역방향 엣지도 레인 라우팅 | 4725 | 4.51 | 14746×21503 |
| 웨이포인트 완화 20패스 | 4725 | **4.28** | 14746×21503 |
| 유니온 멤버 인접(정렬 제약) | 4716 | 4.60 | 14818×19733 |
| 랭크 내 빈틈 압축 | **4385** | 6.01 | 14689×**13911** |

### 복잡도 = 교차(엣지간·카드) 우선

지표는 셋을 같이 본다. 우선순위는 **엣지간 교차 > 카드 교차 > 길이**.

- `crossings` — 엣지가 지나가는 **남의 카드** 수 (양 끝 카드는 제외), 호길이 32px 균등 샘플.
- `tangles` — 서로 **교차하는 엣지 쌍**의 수. 정의가 중요하다: (1) 세그먼트 쌍이 아니라 엣지
  쌍이다 — 두 엣지가 몇 번을 교차하든 눈에는 한 번의 엉킴이다. (2) **끝점을 공유하는 쌍은
  세지 않는다** — 허브로 들어오는 참조 100개는 도착점에서 서로 만나지만 그건 부채꼴이 모이는
  것이지 교차가 아니다. 처음엔 이 둘을 다 놓쳐서 세그먼트 쌍을 끝점 공유까지 포함해 셌고,
  값이 10% 부풀어 있었다(544195 → 487940). 방향성 결론은 바뀌지 않았다.
- `avg len` — 엣지 양 끝의 직선 거리.

| 변경 | avg len | card/엣지 | edge-x/엣지 |
|---|---|---|---|
| 유니온 인접까지 | 4716 | 4.60 | — |
| 랭크 내 빈틈 압축 | 4385 | 6.01 | (구지표 190.0) |
| **압축 되돌림 + 스무딩 80 + 동점교환 + 시프팅** | **4580** | **4.03** | **246.4** |

압축(짧은 엣지)은 되돌렸다. 길이는 5% 줄지만 카드가 평면을 57% 더 차지해 카드 교차 +42%,
엣지 교차 +28% 였다. 교차가 우선이면 손해다.

**측정해 보고 버린 것들** (모두 재현 가능):

- *network simplex 랭킹* (`core/src/ranking.rs`, 옵션): Σ|랭크 차이| 를 정확히 최소화한다.
  모든 엣지 전진(minlen 1)이면 72열이 되어 평균 길이 8256, 비트리 간선을 minlen 0 으로 풀면
  스팬 24888 → 8785 지만 랭크가 넘쳐 높이 균형이 이득을 반납한다(5927). 스팬 최적과 픽셀
  최적은 다른 목표다.
- *정렬 재시작*: 4개 초기 순서에서 다시 정련 — 주 컴포넌트에서 0%, 시간은 18배.
- *정렬 반복 증가*: 14/8 과 60/40 이 같은 그림. 평평한 골짜기지 덜 익은 게 아니다.
- *말단 노드를 가장자리로*: 하드 재배치와 소프트 바이어스 둘 다 엣지 교차를 137 → 150~159
  로 **악화**시킨다. 리프 자신의 입력 엣지가 랭크를 가로질러야 하고, 그 횡단이 리프가 막고
  있던 것보다 더 많이 교차한다.
- *시프팅 윈도우 확대*: 카드 교차는 계속 줄지만(160 에서 3.65) 엣지 교차와 길이가 오른다.
  24 에서 멈춘 이유.

**교차 vs 길이는 파레토 경계다.** 목표를 "최대한 꼬이지 않게, 그 다음 겹치지 않는 선에서
최대한 짧게" 로 두고 더 밀어 봤는데, 길이를 줄이는 모든 수단이 교차를 사 온다:

| 시도 | avg len | card/엣지 | edge-x/엣지 |
|---|---|---|---|
| **현행 (교차 최소점)** | 4580 | 4.03 | **137.4** |
| 가로 압축(카드를 이웃 쪽으로) | **4261** | 5.72 | 180.6 |
| 랭크 내 빈틈 압축 | 4385 | 6.01 | (구지표 190.0) |

가로 압축은 카드가 컬럼 밖으로 나오면서 레인을 막는다 — 길이 −7% 에 교차 +31%.

교차만 노린 시도도 전부 졌다: 레인을 목적지 순으로 정렬(137→177, 진입부에서 꼬임),
타깃별 레인 공유(137→176, 스파인까지 기어올라야 함), 포트 인식 정렬(137→140, 필드 순서로
대상을 정렬해도 랭크 단위 이득이 이를 상쇄).

**남은 가장 큰 손잡이는 번들링이다** — 평행 필드 엣지를 하나로 합치면 3960 → 3121 엣지,
엣지 교차가 엣지당 138 → 107, 총량 −39%. 사용자 토글(⌘E)이라 기본값을 바꾸지 않았다.

### laminar flow — 방향 단조성과 교차는 상충한다

"엣지가 laminar flow 처럼" 이라면 역류가 없어야 한다. 지금은 3960 중 2371 이 오른쪽에서
왼쪽으로 흐른다. 이건 BFS 랭킹이 실현 가능한 레이어링이 아니어서다.

| 랭킹 | 역류 | avg len | card | edge-x |
|---|---|---|---|---|
| BFS (기본) | 2371 | 4580 | 4.03 | 137.4 |
| simplex, 단조 | 449 | 8184 | 6.06 | 150.0 |

이 스키마는 진짜 순환(User → Repository → owner → User)이 많아서 좌→우 단조 배치는 37열이
아니라 72열을 요구하고, 그 폭이 길이 +79%·카드 교차 +50%·엣지 교차 +9% 를 만든다. 수치로
어느 한쪽이 이기지 않으므로 **`Left-to-right flow` 토글(⌘L)** 로 빼서 눈으로 고르게 했다.
기본값은 끔.

### 유니온 응집### 유니온 응집

유니온은 왼쪽에 부모 타입, 오른쪽 컬럼에 배리언트가 모여 있어야 한다(사용자 요구).
배리언트끼리는 엣지가 없어서 교차 감소가 이들을 묶어 둘 이유가 없고, 그냥 두면 랭크
전체에 흩어져 유니온이 "화살표 분사"로 보인다. `layout::Cluster` 로 부모+멤버를 넘기고,
정렬 스윕이 끝난 뒤 각 클러스터를 **한 덩어리로 모아** 원래 중앙값 자리에 놓는다. 그 뒤
블록 단위 transpose 를 한 번 더 돌려 덩어리째 교차가 적은 자리로 미끄러지게 한다.
높이 균형 단계도 클러스터를 알고 있어서 덩어리를 쪼개지 않는다(단, 캡의 절반보다 큰
클러스터는 예외 — 멤버 수십 개짜리 유니온 하나 때문에 그림 전체가 세로로 늘어난다).

결과: 한 컬럼에 모인 유니온 15/42, 사이에 끼어든 것 없이 완전히 붙은 유니온 13/42
(이전 0), 멤버 간 평균 거리 3405 → 3255, world 높이 21503 → 19733(8% 단축), 평균 엣지
길이는 사실상 동일(4725 → 4716), 교차는 4.28 → 4.60(+7.5%).

**배리언트를 부모 랭크+1로 강제하는 것은 측정 후 채택하지 않았다.** 한 컬럼에 모이는
유니온이 15 → 18로 늘지만 평균 엣지 길이 +14%, 교차 +35%를 치른다. 배리언트가 다른
컬럼에 있는 건 루트에서 더 짧은 경로로 먼저 닿기 때문이고, 그걸 뒤집으면 그 타입의
다른 엣지가 전부 길어진다.

측정해 보고 **버린** 것들: 타깃별 레인 번들링(스파인이 중앙값에 앉아 엣지가 기어올라감 —
교차 +88%), 레인을 랭크 사이 거터로 이동(차이 없음), longest-path 랭킹 유지(단조성은 얻지만
깊이가 두 배라 길이·교차 모두 악화). 라우팅 자체는 확실히 기여한다 — 끄면 4.28 → 6.69.
